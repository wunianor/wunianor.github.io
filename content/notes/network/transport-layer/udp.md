## 1. UDP报文格式

![UDP 报文格式：16位源端口号、16位目的端口号、16位UDP长度与16位UDP检验和构成 8 字节首部，其后为数据](/images/notes/network/transport-layer/udp/image-008.svg)

1. **16位源端口号**：确定是发送方的哪个进程发的
2. **16位目的端口号**：用于确定交付给应用层的哪个进程
3. **16位UDP长度**：整个报文（首部（定长 8 字节）+ 数据）的长度
4. **16位检验和**：用于检验收到的首部和数据是否正确，出错则丢弃
5. **数据**：正文内容

## 2. UDP特点

**UDP的5个特点**：

1. **无连接**：发送数据不需要建立连接
   - 知道对端的IP和端口号就直接进行传输，不需要建立连接
2. **不可靠**：没有确认，重传机制
   - 没有确认机制，没有重传机制；如果因为网络故障该段无法发到对方，UDP协议层也不会给应用层返回任何错误信息
   - **先发的报文不一定先收到**：即不保证报文的接收顺序与发送顺序相同；UDP具有接收缓冲区，但是这个接收缓冲区不能保证收到的UDP报的顺序和发送UDP报的顺序一致，这也是不可靠的体现
   - **如果UDP接收缓存区满了，那么后来的报文就会被丢弃掉**：这也是不可靠的体现
   - **UDP是没有发送缓冲区的**：UDP没有真正意义上的发送缓冲区，调用write()/sendto()之后，正文直接交给内核的数据结构进行发送，由内核将数据传给网络层协议进行后续的传输动作
3. **面向数据报**：每次发送的都是一个完整的报文
   - 应用层交给UDP多长的报文，UDP原样发送，既不会拆分，也不会合并，也就是不能够灵活的控制读写数据的次数和数量
   - **UDP是面向数据报的，也就是发n次就一定得接收n次**：每次发送的都是 一个 完整 的报文
     - 用UDP传输100个字节的数据：如果发送端调用一次sendto，发送100个字节，那么接收端也必须调用对应的一次recvfrom，接收100个字节；而不能循环调用10次recvfrom，每次接收10个字节
4. **UDP的报文（首部+数据）最大大小为64KB**：UDP协议首部中有一个16位的最大长度，也就是说一个UDP能传输的数据最大长度是64K（包含UDP首部）
   - 然而64K在当今的互联网环境下是一个非常小的数字；如果我们需要传输的数据超过64K，就需要在应用层手动的分包，多次发送，并在接收端手动拼装
5. **UDP的socket是全双工的**：UDP的socket既能读，也能写

## 3. 基于UDP的应用层协议

1. NFS：网络文件系统
2. TFTP：简单文件传输协议
3. DHCP：动态主机配置协议
4. BOOTP：启动协议（用于无盘设备启动）
5. DNS：域名解析协议

## 4. UDP内核数据结构

![UDP 内核数据结构：UDP 首部四个 16 位字段由 struct udphdr 描述，报文由 sk_buff 承载，head、data、tail、end 划分缓冲区](/images/notes/network/transport-layer/udp/image-013.svg)

### 4.1. UDP首部与内核结构体

内核用 `struct udphdr` 描述 UDP 首部，四个字段都是 16 位：源端口号、目的端口号、UDP长度、UDP检验和。读走前 8 个字节，剩下的就是有效载荷。

### 4.2. 报文的缓冲区：sk_buff

Linux系统是用C语言写的，内核用 `struct sk_buff` 承载一个报文，其中四个字段（`head` / `data` / `tail` / `end`）划出缓冲区：`head` 指向分配内存的起始，`data` 指向有效数据的起始，`tail` 指向有效数据的末尾，`end` 指向分配内存的末尾。加协议头时 `data` 前移（往 headroom 里写），剥协议头或取数据时 `data` 后移。

### 4.3. UDP报文的发送过程

以客户端调用一次 `sendto()` 发送 100 个字节为例，内核里大致是这几步：

1. 用户态调用 `sendto()` 把数据和目的地址交给内核；如果这个 socket 还没有绑定源端口，内核会先给它分配一个临时的源端口
2. 内核查路由表，确定这次从哪块网卡发出、源 IP 用哪一个
3. 内核构造一个 sk_buff：先把 UDP 首部要占的位置预留出来（就是图上 headroom 的位置），再把应用层的数据填进有效数据区（就是图上 `data` 开始的那一段）；数据太长、超过 MTU 允许的长度时，会在这里被切成多个分片
4. 在预留的位置上填 UDP 首部（就是图上 `struct udphdr` 的四个字段）：源端口号、目的端口号、UDP长度、UDP检验和
5. 交给网络层：补上 IP 首部并算出校验和，再由邻居子系统填上 MAC 头，最后交给网卡驱动发出

### 4.4. UDP报文的接收过程

1. 网卡收到数据帧，驱动把整帧放进一个 sk_buff（`data` 指向数据起始、`tail` 指向数据末尾），交给协议栈
2. IP 层校验首部，按首部里的协议号看出这是 UDP
3. 校验 UDP 首部和检验和，检验和不正确就直接丢弃
4. 用**目的端口号**在 UDP 的哈希表里找到对应的 socket，这一步就是分用；找不到就回一个 ICMP 端口不可达
5. 找到 socket 后，把这个 sk_buff 挂到它的接收队列上排队；排队的数据超过接收缓冲区上限就丢弃
6. 用户态 `recvfrom()` 从队列里取出一个 sk_buff，把 8 字节 UDP 首部之后的有效载荷拷贝到用户缓冲区，然后释放这个 sk_buff

**所以「发一次就得收一次」**：一次 `sendto()` 在内核里就是一个 sk_buff，接收端一次 `recvfrom()` 取走一个 sk_buff；接收缓冲区满了，报文就被丢弃，这也正是UDP不可靠的体现。
